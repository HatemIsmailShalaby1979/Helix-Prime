## 2. Pilot scope

Human-supervised, local-first controlled pilot limited to **synthetic or explicitly
consented data**. It exercises the real control plane, six engines, nine agents, GM
aliases, C7 sibling contracts (in-process transport), audit, classification,
authorization, persistence, and backup/restore — with **no** irreversible, financial,
personnel, compliance, ICT, or external-communication action.

Proven artefacts:
- 14 `controlled_pilot` release gates green → `CONTROLLED_PILOT_READY`
- 15-check verification harness green
- Deterministic pilot dry-run green (vertical slice success + denial, sibling round-trip,
  timeout/retry/dead-letter, restart, backup/restore, audit integrity, tenant isolation)

## 3. Approved synthetic / consented data boundary

- Source of truth: `release/go-no-go.json` → `data_scope: SYNTHETIC_OR_CONSENTED_ONLY`.
- Every input payload must be `is_sample: true` (synthetic) or carry explicit consent
  evidence. `data_mode = "real"` is prohibited for the pilot.
- No real customer data, real secrets, tokens, or credentials are entered, logged,
  committed, or persisted.
- Any use of non-synthetic, non-consented data is out of scope and prohibited.

## 4. Allowed workflows

- Controlled vertical slice (WFM → RTA → OPS → Compliance → HR/L&D → CRM/CX → SAMI).
- Local persistence, replay, idempotency, audit logging, classification, authorization.
- C7 sibling contracts over in-process/in-memory transport.
- Backup / restore / rollback on isolated synthetic state.
- Bounded synthetic soak (explicit caps; no unbounded growth).

## 5. Prohibited workflows

- Any irreversible, financial, personnel, compliance, ICT, or external-communication action.
- Autonomous (non-approved) irreversible actions.
- Network sibling transport / cloud deployment / external IdP / cloud observability.
- Use of real (non-synthetic, non-consented) data.
- Emitting a bare `PRODUCTION` label or fabricating a `production_approved` sign-off.

## 6. User / role responsibilities

| Role | Responsibility |
|------|----------------|
| Operator (pilot lead) | Runs gate + dry-run, reviews evidence, owns the pilot run. |
| Reviewer | Independently reviews the evidence pack and sign-off conditions. |
| Data controller | Confirms data is synthetic or consented; nothing else. |
| Sibling service proxy | Runs deterministic fake siblings over in-memory transport only. |
| On-call / incident handler | Follows `incident-response.md`; never acts irreversibly without approval. |

No single role may both run the gate and unilaterally approve the sign-off (SOD).

## 8. Daily startup and health checklist

1. `python3 scripts/health_check.py` → `READY=True`.
2. `python3 -m pytest -q` → 307 passed (regression).
3. `python3 scripts/release_gate.py --profile controlled_pilot` → `CONTROLLED_PILOT_READY`.
4. `python3 scripts/pilot_dry_run.py` → `CONTROLLED_PILOT_READY`, exit 0, all checks green.
5. Confirm working tree clean and no temp state left behind.
6. If any step is red/exceptional, halt and follow `incident-response.md`; do not proceed.

## 9. Incident escalation path

Follow `../incident-response.md`:
- SEV-3 (Info) → log only.
- SEV-2 (Degraded) → component unavailable; pilot may continue with the rest.
- SEV-1 (Critical: control-plane, audit, or persistence unavailable) → stop writers,
  preserve audit DB, restore from latest backup, escalate to operator on-call.
- Audit chain tamper detection → stop immediately (SEV-1), preserve DB, investigate,
  do not continue until resolved.
- Any unresolved incident blocks the pilot.

## 10. Backup / restore procedure

See `../backup-restore-guide.md`. Rule: backup → restore into a **clean, empty** target,
never in-place. Gate/dry-run prove a synthetic backup→restore→verify cycle and confirm
the restored audit chain verifies. `release.backup.schema_compatible` fails closed on
unsupported schema versions.

## 11. Rollback procedure

`release.backup.rollback_manifest(previous, active, target_path=...)` restores the
previous release identity and records a rollback marker. Rollback restores the previous
committed manifest — never the live database. Proven green by the `rollback` gate.

## 12. Evidence collection procedure

- Gate runs write `evidence/releases/<timestamp>/` (`release-gate-summary.json`,
  `release-manifest.json`, `harness-results.json`).
- Pilot dry-run writes `evidence/pilot/<timestamp>/` (`pilot-dry-run-summary.json`,
  `pilot-metrics.json`).
- All `evidence/*` is gitignored; only `evidence/README.md` is committed.
- Record only what a run actually produced; never fabricate evidence.

## 13. Pilot success metrics

From `../metrics.md` / `release/pilot_metrics.py`, measured on the SYNTHETIC dry-run:
workflow completion rate, approval denial rate, timeout rate, retry rate, dead-letter
rate, audit-verification rate, data-classification and tenant-isolation violation counts,
model-unavailable count, sibling-transport-failure count, and exec-time percentiles.
Proposed pilot thresholds and production SLOs are explicitly NOT validated or claimed.

## 14. Pilot pause / termination conditions

- Any red gate or dry-run check → pause and investigate.
- Any data/tenant-isolation violation or audit-chain tamper → terminate/halt, escalate.
- Unresolved SEV-1 incident → halt.
- Expired or missing sign-off → no further pilot workload.
- Exit/graduate criteria: all checks green for the session, reviewer review recorded,
  every `conditional` condition closed, and documented metrics gathered. Exit does NOT
  imply `PRODUCTION_READY`.
